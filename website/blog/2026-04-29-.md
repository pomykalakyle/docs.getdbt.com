> *"By all means, move at a glacier's pace."*
> — Miranda Priestly, *The Devil Wears Prada*

There's another scene in *The Devil Wears Prada* that I think about more than that one. Miranda turns to Andy and explains, with complete patience, that the cerulean blue in Andy's "lumpy sweater" didn't come from nowhere — it traced back through fashion decisions made years earlier, by people who thought carefully about every choice. The whole chain, invisible to Andy, was built on deliberate curation.

That's what documentation architecture feels like to me. Developers ask a question, get an answer, keep working. They don't see the decisions behind it — what to include, how to structure it, where the gaps are, what needs updating. But those decisions shape every answer they get, including the ones coming from AI.

How we bring docs closer to developers — and why that architecture matters more than ever — is what this post is about.

## The problem: docs exist, but AI can't reach them

There's a scene in *The Devil Wears Prada* where Miranda dissects Andy's "lumpy blue sweater" — tracing it back through fashion decisions made years earlier by people Andy would never think about. Andy assumed she'd opted out of the whole chain. She hadn't.

A developer asking an AI assistant a question is in a similar position. The answer feels direct and immediate, but it traces back through whatever the AI was trained on or fetching from. If that source is outdated, incomplete, or — worse — AI-generated content feeding back into AI answers with no one checking the loop, the whole chain is wrong and no one knows it.

The docs at [docs.getdbt.com](https://docs.getdbt.com) exist to be that reliable source. But until recently, the dbt MCP server couldn't reach them.

## The research: what the data actually showed

Earlier this year I built out a [research doc](https://www.notion.so/dbtlabs/docs-context-research-30dbb38ebda780d1b067e2206b5b1845) to answer a simple question: where does the dbt MCP server actually sit in how people work? I queried MCP server telemetry in dbt Platform, and what I found made the path forward obvious.

The dbt MCP server had already exceeded its full-year 2025 volume in just the first two months of 2026 — usage roughly doubling in that window. The user base is real, active, and growing fast. <!-- 📊 decide: you may want to add specific numbers here from the research doc, e.g. total tool events, accounts, users -->

The server had eight toolset categories — CLI, Semantic Layer, Discovery, Admin API, SQL, Codegen, Fusion, Server Metadata. Not one of them could access docs.getdbt.com. When an agent needed to answer *"how do I configure incremental models?"* — it was on its own.

We already had a solid foundation for AI-readable docs:

- `docs.getdbt.com/llms.txt` — a page index for AI systems
- `docs.getdbt.com/llms-full.txt` — full docs content in a single file
- `.md` suffix support on any docs page for clean markdown output
- A published [`fetching-dbt-docs` skill](https://skills.sh/dbt-labs/dbt-agent-skills/fetching-dbt-docs) that teaches AI agents how to access our docs via web requests, installed across Claude Code, Copilot, Gemini CLI, Amp, and others

The skill approach worked. But it had a friction problem: the agent had to know the skill existed, install it, and perform web fetches as a workaround. Adding docs tools directly to the MCP server means existing users get the capability automatically, with no action required on their part. The reach difference between the two approaches was not close. <!-- 📊 decide: the specific comparison (MCP accounts vs. weekly skill installs) is in the research doc if you want to include it -->

## The solution: delivering The Book

In *The Devil Wears Prada*, there's a ritual: every evening, "The Book" — Miranda's nightly reading — is delivered to her apartment. She doesn't go to the office to get it. It arrives, in her space, when she needs it.

That's the standard I was trying to meet. Developers shouldn't have to leave their workflow to find documentation. The docs should arrive — in the tool they're already using, at the moment they need them.

The dbt MCP server could already handle lineage lookups, test runs, Semantic Layer queries, job debugging. But ask it *"what's the syntax for a snapshot strategy?"* and it had to improvise. Training data. Best guess. The Book wasn't being delivered.

We added two tools to the dbt MCP server under a new **"Product Docs"** category — the ninth toolset:

- **[`search_product_docs`](https://docs.getdbt.com/docs/dbt-ai/mcp-available-tools?version=2.0#product-docs)** — searches docs.getdbt.com and returns titles, URLs, and relevance-ranked descriptions for pages matching your query.
- **[`get_product_doc_pages`](https://docs.getdbt.com/docs/dbt-ai/mcp-available-tools?version=2.0#product-docs)** — fetches the full markdown content of one or more docs pages by path or URL.

The workflow mirrors how a human would use the docs: search first to find what's relevant, then fetch the full content. The difference is that it happens inside whatever AI tool you're already using, without a context switch.

Because these tools hit public URLs, they work without a dbt Cloud account. Every dbt user — open source or Platform — gets docs access through MCP, for free.

Alongside this, the DX team has been building out [dbt agent skills](https://skills.sh/dbt-labs/dbt-agent-skills) — including the `fetching-dbt-docs` skill — which remain the best path for agents not connected via MCP. The skill and MCP tools complement each other rather than compete. The skill is the workaround that proved the demand. The MCP integration is the native solution.

## What this changes day to day

The practical before/after is simple. Before: write a macro, hit an unfamiliar function, alt-tab to a browser, search docs, read the page, return to your editor, try to remember where you were. After: ask Claude directly, get an answer grounded in actual current documentation, keep coding.

The Book arrived. No context switch required.

For analysts exploring a shared project, it means understanding what a model does without navigating to a separate tab. For teams working across different dbt setups, it means consistent, authoritative answers regardless of where they're working or who's asking. For the docs team, it means the work we put into writing and maintaining docs.getdbt.com is doing more than it was before — reaching developers where they actually are.

## What's next

This is a first step, and an honest one. A few things on the radar:

**Version-aware docs fetching.** Right now these tools return current documentation. A developer on dbt Core 1.5 asking about incremental strategies gets 2026 docs. Version-aware routing — returning the right page for the right dbt version — is the next meaningful improvement, and it's on the roadmap.

**Smarter search ranking.** Relevance is good. Relevance tuned to dbt-specific concepts and query patterns would be better.

**Coverage gaps as a signal.** MCP usage will surface which questions return weak results — pages that are missing, thin, or outdated. That's a direct queue for the docs team, and a feedback loop that didn't exist before.

**A dedicated dbt docs MCP server.** It's not the right call right now — one coherent product with an active existing server is the right place to start — but in the future, a standalone docs server could reach every MCP client regardless of whether they use the dbt MCP server at all.

## Conclusion

Miranda's point about the cerulean sweater wasn't really about fashion. It was about invisible chains — that every choice ripples further than the person making it can see, and that the quality of the source shapes everything downstream.

That's where docs are now. A developer asks an AI a question and gets an answer without ever opening a browser. They don't see the decisions behind it — the structure, the accuracy, the gaps that got filled. But those decisions are in the chain. They always were. The difference is that now, they travel faster and reach further than ever before.

The glacier pace is gone. The current runs fast. And what's in the water matters.
